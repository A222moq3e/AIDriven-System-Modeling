# **Backend Documentation**

## **1\. Overview**

The backend is built with Node.js and Express, designed as a simple API layer that receives requests from the client, processes them, and stores or retrieves data from MongoDB. The system follows a straightforward flow: the client sends a request, Express routes it to the appropriate controller, and the controller handles validation, business logic, and communication with external services like OpenAI when needed. MongoDB is used to persist data such as prompts, generated diagrams, or user-related information. The goal of this backend is to stay predictable, lightweight, and easy to extend. Each endpoint returns structured JSON so the frontend can consume responses consistently without extra parsing or assumptions.

---

## **Schemas**

The backend uses two main MongoDB collections: **User** and **Diagram**. Each schema is designed to stay minimal while storing only the information required for authentication, ownership, and diagram generation.

### **User Schema**

The User schema represents anyone who interacts with the system. It stores a unique identifier, basic profile information, and a timestamp for when the account was created. This keeps authentication simple while allowing diagrams to be linked back to a specific user.

**Fields:**

* **id** – unique identifier generated by MongoDB

* **email** – user’s login email

* **name** – user’s display name

* **createdAt** – automatic timestamp for when the user account was created

This is intentionally lightweight so it can support login, personalization, and data ownership without unnecessary complexity.

---

### **Diagram Schema**

The Diagram schema stores every generated diagram along with the user who created it. Each entry contains the input prompt, the Mermaid code produced by the system, and the diagram type. This allows the frontend to quickly display saved diagrams and regenerate them when needed.

**Fields:**

* **id** – unique identifier for the diagram

* **userId** – references the user who created it

* **prompt** – the text input describing the diagram

* **mermaidCode** – the generated Mermaid syntax

* **type** – type of diagram (flowchart, sequence, class, ERD, etc.)

* **createdAt** – timestamp marking when the diagram was created

The structure keeps diagrams easy to query, filter by user, and render in the UI.

---

## **3\. Response Format**

Every endpoint returns a JSON response using the same structure to make integration easier. Successful responses include a `success` flag and the payload, while errors provide a readable message. Here is the standard format:

### **Success Response**

`{`  
  `"data": {`  
    `"mermaid": "sequenceDiagram ...",`  
    `"type": "sequence"`  
  `}`  
`}`

This keeps the frontend logic simple: if `success` is true, the UI can directly use the `data` object.

### **Error Response**

`{`  
  `"message": "Invalid prompt. Please provide a diagram description."`  
`}`

Errors always return a clear message so the frontend knows what went wrong without guessing. The error format is intentionally minimal so the backend can evolve without forcing UI changes.
